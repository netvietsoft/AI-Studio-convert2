======================================================================


Agent hoạt động theo mô hình:


TASK SCANNER
→ ACTIVE TASK
→ PREFLIGHT
→ EXECUTE
→ TEST / VALIDATE
→ COMMIT + PUSH nếu có code

Mỗi lần scan:


1. Liệt kê các file/folder trong Task Drive.
2. Bỏ qua:
   - LEGACY_*
   - SUPERSEDED_*

5. Chỉ nhận Task có STATUS=ACTIVE.
6. Kiểm tra dependency / assignee / priority / modified time.
7. Chọn Task hợp lệ chưa hoàn thành ở revision hiện tại.
8. Preflight và thực thi ngay.

- merge protected main/master;
- production deploy;
- publish Google Play;
- release public package;
- gửi thay đổi trực tiếp tới production users.


B. DESTRUCTIVE ACTION
- xóa database;
- xóa bucket;
- xóa production data;
- force push;
- rewrite published history;

- overwrite accepted freeze/evidence.


C. SCOPE EXPANSION
- sửa module ngoài scope;
- mở phase mới;

D. FROZEN COMPONENT CHANGE
- frozen API;
- frozen model;
- frozen contract;
- frozen acceptance gate;
- frozen architecture.


E. CREDENTIAL / ACCOUNT / PERMISSION
- API key mới;
- OAuth mới;
- secret production;
- quyền Play Console;
- quyền server/cloud chưa được cấp.


F. MONEY / PAID RESOURCE
- mua API credit;
- thuê GPU;
- bật paid cloud;
- nâng subscription;
- mua service/domain.


G. EXTERNAL COMMUNICATION
- gửi email/ticket/message ra ngoài;
- gửi cho khách hàng/đối tác;
- publish tài liệu ra ngoài tổ chức.


Nếu Task đã cấp quyền rõ cho một trong các hành động trên:

9. PHYSICAL DEVICE VISUAL EVIDENCE & STORAGE HYGIENE


9.1. VISUAL EVIDENCE GATE — BẮT BUỘC
Khi Task có kiểm thử UI, ảnh, video frame, rendering, camera, editor hoặc output trực quan trên thiết bị vật lý:
- Agent phải test trên thiết bị thật khi Task yêu cầu physical-device evidence.
- Agent phải chụp screenshot/frame bằng ADB hoặc cơ chế capture thực tế, không dựng ảnh giả để làm bằng chứng.
- Ảnh tạm được lưu theo cấu trúc:
  .ai/evidence/visual/<TASK_ID>/<run_id>/
- Mỗi artifact phải có metadata tối thiểu:
  task_id, run_id, commit_sha, device, adb_serial, screen_or_feature, test_case, expected_result, captured_at, sha256.
- Agent phải upload evidence cần audit lên canonical Report Drive. Git chỉ lưu manifest, metadata, hash và các ảnh final/selective khi thật sự cần; KHÔNG commit hàng loạt screenshot/raw frame vào Git vì xóa file sau đó vẫn làm phình Git history.
- Khi evidence đã upload xong, Agent phải phát:
  CONVERT2_EVENT_V1
  type: VISUAL_REVIEW_READY
  kèm task_id, head_sha, run_id và đường dẫn artifact/manifest.
- Visual PASS không được tự tuyên bố chỉ dựa trên Agent thực thi. Phải qua Visual AI Auditor/Reviewer độc lập khi Task hoặc gate yêu cầu.


9.2. VISUAL REVIEW
Auditor kiểm tra tối thiểu:
- đúng màn hình/chức năng/test case;
- layout, text, icon, clipping, overflow, alignment;
- thay đổi đúng vùng yêu cầu;
- không lem sang vùng cấm;
- preservation của vùng không chỉnh sửa;
- artifact, biến dạng, texture, naturalness;
- provenance khớp commit/run/device;
- ảnh đủ rõ để audit.
Verdict:
VISUAL_PASS
VISUAL_NEEDS_FIX
VISUAL_BLOCKED_EVIDENCE_MISSING


9.3. CLEANUP SAU KHI UPLOAD/REPORT — BẮT BUỘC
Mục tiêu: không để screenshot/raw frame làm đầy bộ nhớ điện thoại hoặc máy build.


Sau khi:
1. artifact đã upload thành công lên canonical Report Drive;
2. SHA-256/manifest đã được ghi nhận;
3. report/checkpoint tương ứng đã được tạo;
Agent phải xóa bản tạm khỏi:
- thiết bị Android (/sdcard/... hoặc thư mục capture tạm);
- workspace local (.ai/evidence/visual/... raw/temp);
- thư mục temp của runner nếu còn bản sao.


Không được xóa trước khi xác minh upload thành công và artifact remote có thể truy cập.


Sau cleanup phải ghi log:
VISUAL_EVIDENCE_CLEANUP
task_id
run_id
remote_artifact_count
local_deleted_count
device_deleted_count

XXV. TASK CREATION MUST DISPATCH COMMAND BUS — MANDATORY
======================================================================


A Task document created in canonical Task Drive is NOT considered dispatched merely because STATUS=ACTIVE.


Whenever Tony/System Audit/Watchdog creates or materially updates an ACTIVE Task, the same workflow MUST ensure the execution signal reaches the GitHub Agent Command Bus.


Required chain:
TASK CREATED/UPDATED IN TASK DRIVE
→ WRITE/UPDATE COMMAND BUS INPUT (for example .ai/commands/NEXT_COMMAND or the repository's current canonical command file)
→ COMMIT + PUSH COMMAND CHANGE
→ VERIFY A NEW GITHUB ACTIONS / COMMAND BUS RUN WAS TRIGGERED FOR THAT Task ID/revision
→ RECORD run_id / workflow URL / dispatch commit SHA
→ only then mark TASK_DISPATCHED.


Hard rule:
TASK_CREATED != TASK_DISPATCHED.
TASK_ACTIVE != ACTION_TRIGGERED.


The Watchdog/Orchestrator MUST NOT report “Agent is running” based only on creation of a Google Drive Task.
It may say Agent is running only after a matching GitHub Actions/Command Bus run is observed.


If Task creation succeeds but command dispatch does not:
STATUS = TASK_CREATED_DISPATCH_PENDING
The Watchdog must attempt the canonical dispatch path automatically when authorized and technically available.
If it cannot write/commit/push the command bus input, record the exact blocker and do not falsely claim execution.


ANTI-DUPLICATE:
Before dispatch, compare Task ID + Task revision/hash + last dispatched command. Do not trigger duplicate runs for the same unchanged Task revision.
A materially updated ACTIVE Task revision MUST be eligible for a new dispatch.


MULTI-AGENT:
For multiple independent ACTIVE Tasks, dispatch each eligible task to a distinct safe execution lane/runner when supported. Respect file locks, branch/worktree isolation, dependencies, frozen modules, and merge-conflict prevention.


AUDIT REQUIREMENT:
Every scan must reconcile three states separately:
1. TASK_CREATED — exists in Task Drive.
2. TASK_DISPATCHED — matching command commit/action run exists.
3. TASK_EXECUTING/COMPLETED — runtime/report evidence exists.
A mismatch is a process defect requiring correction.

A Task is not considered running until a matching Command Bus/GitHub Actions execution is observed.
